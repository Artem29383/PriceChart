# Observability Dashboard Lab — отдельная лаборатория

**Цель:** научиться проектировать интерфейсы облачного мониторинга и конфигурируемые
дашборды в стиле задач Cloud X: типобезопасные контракты, переиспользуемые панели,
управление состоянием, производительность, работа с временными рядами,
подключение сервисов и независимая поставка UI-модулей.

## Где находится

- `#/observability` — новая лаборатория (открывается по умолчанию).
- `#/charts` — оба графика PriceChart, не изменённые обучением Observability.

Обе страницы находятся в **одном репозитории**, используют один Vite dev server и
разные каталоги исходников. React-компоненты графиков не зависят от лаборатории;
лаборатория не импортирует графики. Для простого переключения используется hash
navigation без дополнительной routing-библиотеки.

## Структура

```text
src/
  app/
    App.tsx                   корневое переключение лабораторий
    ChartsPage.tsx            существующая демонстрация обоих PriceChart
    navigation.css
  chart/                      личный график и независимая reference-реализация
  labs/
    observability/
      ObservabilityLab.tsx     оболочка новой лаборатории
      components/
        MetricPanel.tsx       демонстрационная заглушка панели
      data/
        mockMetrics.ts        детерминированные фикстуры метрик, без HTTP
        mockMetrics.test.ts
      model/
        types.ts              модели данных и конфигурации
      styles/
        observability.css
```

`PriceChart.tsx`, `ReferencePriceChart.tsx` и существующий chart engine не
нужно изменять на упражнениях новой лаборатории.

## Что уже сделано (этап 00)

- Готовый интерфейс лаборатории в тёмном стиле.
- Типы `MetricPoint`, `MetricSeries`, `MetricDefinition`,
  `DashboardPanelConfig`, `DashboardConfig`.
- Четыре серии данных: CPU, Memory, HTTP Requests, API Latency.
- У каждой серии timestamp в миллисекундах, значение `number | null`;
  для Latency есть отсутствующие значения.
- Начальная конфигурация из четырёх панелей.
- Отдельный тест на фикстуры и совместимость панели с определением метрики.
- Рабочее переключение между лабораториями; рендереры графиков не используются.

**Важно:** существующие панели намеренно не имеют редактирования, сохранения
конфигурации или графической визуализации. Мы будем реализовывать это вместе.

## Порядок работы — одна практическая задача за раз

### 01 — Состояние конфигурации Dashboard (первая задача)
- Разобрать `readonly`, массивы, обновление состояния без мутаций, уникальные идентификаторы.
- Перенести `INITIAL_DASHBOARD` в React State лаборатории.
- Добавить одну кнопку «Добавить панель» и создать новую панель со стабильным ID.
- Затем сделать удаление по ID, защиту от дублей и контролируемый выбор метрики.
- **Критерий:** панель появляется/исчезает без изменений исходной конфигурации.

### 02 — Публичный API и типобезопасная конфигурация
- `satisfies`, discriminated unions для `line/stat/table`, типы опций.
- Управление источником метрик и типом визуализации.
- Разделить `DashboardConfig`, данные временных рядов и UI-state.
- **Критерий:** неправильные комбинации конфигурации ловит TypeScript.

### 03 — Компоненты и архитектура Dashboard Builder
- Переиспользуемые виджеты, инкапсуляция и композиция.
- Props vs Context vs store: выбираем по реальной сложности.
- Тестируем добавление, удаление, изменение типов панели.
- **Критерий:** любая панель работает независимо от остальных.

### 04 — Сохранение и восстановление настроек
- Версия конфигурации, сериализация JSON, runtime-проверка.
- Сохранение в localStorage как временный прототип; затем API.
- **Критерий:** настройки переживают обновление страницы без некорректных данных.

### 05 — Реальная визуализация метрик
- Сначала подключим наш `ReferencePriceChart<T>` через адаптер либо отдельный
  renderer для Observability, сохранив независимость доменных моделей.
- Пропуски, шкалы, разные единицы измерения и временные диапазоны.
- **Критерий:** панели показывают корректные CPU, Memory, RPS и Latency.

### 06 — Real-time и источники данных
- Polling, SSE, WebSocket (научимся выбирать, а не добавлять всё сразу).
- Отмена запросов, гонки, reconnect/backoff, очистка эффектов.
- Уровни: метрики → data provider → dashboard state → панель.

### 07 — Performance и отладка
- 20–30 панелей, обновления раз в секунду, React Profiler.
- Оптимизируем рендеры, группируем обновления, сравниваем измерения.
- Изучаем Memory leaks, ResizeObserver, rAF и OffscreenCanvas по необходимости.

### 08 — Конструктор, роли пользователей и расширение
- Шаблоны панелей, пользовательские пресеты, конфигурации.
- Разделение доменов, плагины, библиотечный API, обратная совместимость.
- Рассматриваем способы использовать модуль в нескольких продуктовых командах.

### 09 — Module Federation и микрофронтенды
- Host/remote, exposes, shared dependencies, runtime loading.
- Обсуждаем версионирование и контракт микрофронтенда.
- Учебный эксперимент проведём отдельно; текущую Vite-конфигурацию не ломаем.

## Правила парного программирования

- Сначала кратко объясняем механизм и TypeScript-контракты.
- Даём **одну** небольшую задачу. Ученик пишет код, наставник проверяет GitHub.
- Готовую формулу/инфраструктурный код можно попросить целиком — не заставляем
  выдумывать математику.
- Никаких новых готовых конструкторов или больших фреймворков без необходимости.
- Не менять Windows-friendly `127.0.0.1:5173`, не добавлять MSW / service worker.
- Проверки после каждого значимого шага:
  `npm run typecheck && npm run lint && npm run test && npm run build`.

**Начинаем с этапа 01.** Первая практическая цель — сделать
`DashboardConfig` управляемым React-состоянием, не меняя графики.
