# BEFORE / AFTER — Performance Optimized Lab

Маршруты:
- Baseline: `http://127.0.0.1:5173/#/performance-stress`
- Optimized: `http://127.0.0.1:5173/#/performance-optimized`

Базовый Stress Lab **не изменён**. Сравниваем две независимые реализации.

## Обязательно: одинаковые исходные данные

Обе вкладки импортируют одни и те же `PRESETS`, `validateConfig` и
`generateSeries` из `src/labs/performance-stress/workload.ts`.

| Профиль | Панелей | Точек на панель | Точек всего | Интервал |
|---|---:|---:|---:|---:|
| Light | 6 | 300 | 1 800 | 5 секунд |
| Medium | 24 | 2 000 | 48 000 | 1 секунда |
| Heavy | 48 | 10 000 | 480 000 | 250 мс |
| Extreme | 96 | 10 000 | 960 000 | 100 мс |

В каждом графике одна и та же `Float32Array`-последовательность, созданная
тем же детерминированным генератором с теми же параметрами `id`,
`pointsPerPanel` и генерации шумов. Функция динамической последней
точки тоже повторяет baseline:

```ts
const last = series.values[series.values.length - 1] +
  Math.sin(tick / 3 + series.id) * 6;
```

В данных **нет реального сервера** и нет нагрузки на сеть.

## Что изменено

### 1. Не пересоздаём длинные строки SVG каждый тик

**До:** на каждом тике каждый StressPlot проходит N точек,
дважды вызывает `toFixed(2)` и собирает большой `path` строкой.

**После:** при первом появлении графика `minMaxIndices` за O(N)
вычисляет индексы отображаемой истории, рисует её **один раз** на
static Canvas. При каждом тике рисуется только короткий последний
сегмент на отдельном overlay Canvas: O(1).

Статическая линия перерисовывается при изменении размеров контейнера,
новом наборе данных или возвращении в видимость. Это не буквальная
O(1)-стоимость для всех операций — только для регулярного обновления.

### 2. Уменьшение визуальной детализации без потери локальных экстремумов

Алгоритм min/max downsampling делит историю на до 710 блоков и хранит
минимум и максимум каждого блока в исходном порядке. Вместо 10 000
или 100 000 точек на видимой линии остаётся не более примерно 1422
координат, а исходный массив **остаётся неизменённым в памяти**.

В отличие от простого `filter(i % 10 === 0)`, алгоритм лучше сохраняет
резкие пики. Но сглаживание/понижение разрешения **не равно полностью
идентичному рендерингу**: часть промежуточных точек пропущена.

### 3. Сменили SVG на Canvas

Статический слой и последний сегмент — два Canvas. Нет больших
изменений SVG-атрибута `d` и расходов React reconciliation для точек.
Учтена физическая плотность пикселей (DPR до 2).

### 4. Изолировали поток данных от React State

Один `TickBus` распространяет номер тика.
`OptimizedPlot` не вызывает `setState` при каждом обновлении —
небольшая динамическая часть рисуется напрямую в Canvas, значение
обновляется в `textContent` соответствующего DOM-узла.
Это осознанный императивный путь для high-frequency drawing, а не
типичный способ строить весь React UI.

### 5. Не рисуем невидимые графики

Один `IntersectionObserver` для всех панелей, `rootMargin: 200px`.
За пределами видимой области временно нет подписки на новые тики.
При возвращении панель догоняет текущее значение.
ResizeObserver подключён только для видимой панели.

**Различие нагрузки:** одновременно отображаются все 96 карточек DOM,
но активно рисуется только видимая часть. Это намеренно
меняет количество дорогостоящей работы по сравнению с baseline,
хотя данные/профиль тождественны.

### 6. Реактивное управление отделено от потока

React используется для кнопок, профилей, монтирования панелей и
состояния running/paused. Инициализация данных через `useMemo`,
карточки обёрнуты в `React.memo`, но основной выигрыш — отсутствие
массовых React обновлений при каждом тике.

### 7. Временный стресс-тренажёр, не "идеальный production"

Работают: ограничение до 1 млн исходных точек, подтверждение экстремального
профиля, пауза, снятие графиков, восстановление Light, автопауза при
очень низком FPS. Полная блокировка главного потока всё ещё может
не дать нажать кнопку или выполнить автопаузу.

Не добавляли MobX, Web Workers, WASM, реальный backend и
совместные курсоры: они не нужны для исправления найденной нами
проблемы, а усложнили бы сравнение.

## Как сравнивать правильно

1. Выполни `git pull origin master` и `npm run dev`.
2. В базовой вкладке выбери Extreme (96/10 000/100 мс).
3. Запусти, после появления графиков и закрытия confirm запиши 5–10 с
   в **Chrome DevTools → Performance**, сохрани скриншот Summary и Bottom-up.
4. Нажми Pause, перейди в Optimized и выбери ТОТ ЖЕ Extreme.
5. Запиши 5–10 с **после** того, как видимые графики построены.
6. Сравни `Scripting`, `StressPlot` vs `OptimizedPlot`, Long Tasks,
   maxFrameGap и отклик кнопок. Не сравнивай абсолютные значения,
   пока одна запись включает confirm или первичную загрузку.
7. Для чистого сравнения FPS используй `npm run build && npm run preview`.
   Для React Profiler используй dev-режим: в обычном production build
   значения React render могут быть 0 по причине отсутствия профайлера.
8. Прокрути экран с оптимизированной вкладкой: первая отрисовка каждой
   ранее невидимой панели требует O(N)-сканирования, проверь задержки.

**Честное ограничение эксперимента:** оптимизированная версия
отображает с пониженным разрешением и только видимые панели. Это
настоящие оптимизации пользовательского интерфейса, но не
изолированный научный тест одной функции. Чтобы измерить выигрыш
каждой техники отдельно, можно добавить feature flags и A/B тесты.
