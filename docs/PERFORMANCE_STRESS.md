# Performance Stress Lab — измеряем и устраняем лаги

`http://127.0.0.1:5173/#/performance-stress`

Тренажёр для Chrome DevTools / React Profiler. **Отдельная вкладка и папка.**
Не изменяет исходный PriceChart, Observability Lab и Observability Reference.

## Идея

Создаём **намеренно плохой baseline**, а не идеальный дашборд. Нам важно увидеть
причину тормозов, замерить её и затем применить оптимизации по одной с
повторением того же теста.

- При каждом тике меняется последняя точка, но **все** SVG-графики
  пересобирают **весь** `path` из всех `N` точек в React render.
- Нет `React.memo` у графика, нет `useMemo` для пути, нет downsampling,
  нет виртуализации элементов за экраном.
- При этом генерация исходного массива вынесена из update loop:
  `Float32Array` создаётся только при применении нового профиля. Поэтому
  замеряем преимущественно работу React/render, а не случайную регенерацию данных.
- Внутри одного SVG — 1 `path` на линию, а не десятки тысяч узлов DOM.
  Слишком большой `d` всё равно требует вычислений и обработки браузером.

## Нагрузка

| Профиль | Графиков | Точек на график | Всего | Обновление |
|---|---:|---:|---:|---:|
| Light | 6 | 300 | 1 800 | 5 с |
| Medium | 24 | 2 000 | 48 000 | 1 с |
| Heavy | 48 | 10 000 | 480 000 | 250 мс |
| Extreme | 96 | 10 000 | 960 000 | 100 мс |

Есть ручной выбор: можно проверить 6 графиков по 100 000 точек.
Ограничение: максимум **1 миллион точек одновременно**. Перед тяжёлыми
сценариями — подтверждение. Приложение запускается **на паузе** и не запускает
Extreme автоматически.

Кнопки защиты: «Пауза» останавливает обновления, «Снять графики»
полностью размонтирует SVG, «Лёгкий режим» восстанавливает безопасную настройку.
При FPS ниже 10 в трёх последовательных секундных интервалах лаборатория
попытается поставить нагрузку на паузу. **Это best-effort, не гарантия
от зависания**: при полной блокировке main thread кнопки и таймеры тоже
не реагируют. В крайнем случае закрыть вкладку.

## Что измеряем

1. **FPS**: число вызовов requestAnimationFrame за интервал примерно в 1 секунду.
   Зависит от частоты экрана, фоновых вкладок, VSync и общей загрузки ПК.
2. **Задержки кадров**: сколько интервалов между rAF callbacks превысило 50 мс,
   и наибольшая длительность такого интервала. Это **не** duration GPU frame.
3. **Long Tasks**: PerformanceObserver type=`longtask` когда поддерживается;
   число событий за секунду. Показывает блокировку главного потока.
4. **React render**: сумма `actualDuration` от React `Profiler` для
   панелей за 1 секунду и наихудший render одной панели. **Не включает**
   браузерные style/layout/paint и не равна полной длительности кадра.
5. **JS Heap**: `performance.memory.usedJSHeapSize` в Chromium, если
   доступно. Экспериментальный показатель, не полный memory footprint.

HUD отделён от тяжёлой сетки: его секундные обновления не должны
вызывать рендер всех SVG. На изменение настроек и тики панели реагируют
обычно. Для чистых сравнений используем **production build**:

```powershell
npm ci
npm run build
npm run preview
```

React Profiler в обычной production-сборке React отключён, поэтому там \`React render\` и \`React commits\` могут оставаться нулевыми. Для этих метрик используй dev-режим или специальную profiling-сборку.\n\nDev-сервер + React StrictMode и React DevTools сами добавляют накладные
расходы, и это **другие** измерительные условия. Для глубокого анализа
React-компонентов можно отдельно использовать React DevTools Profiler
в режиме разработки. Сравнивай только результаты одной и той же конфигурации
и в одном и том же режиме.

## Порядок эксперимента

1. Открой вкладку `#/performance-stress`. Запиши параметры ПК/браузера.
2. Выбери **Light**, нажми «Старт / применить», подожди 5–10 секунд.
3. Зафиксируй FPS, задержки кадров, Long Tasks и React render.
4. Повтори Medium, затем Heavy. Не начинай с Extreme.
5. В DevTools → Performance сделай запись 5–10 секунд под нагрузкой.
   Смотри Main thread / Long Tasks / Bottom-up / Call tree.
6. В React DevTools → Profiler найди компоненты `StressPlot`.
   Проверь, почему обновляются все панели.
7. Останови нагрузку и сообщи числа или пришли скриншот профайлера.
8. **Только после baseline:** уменьшаем повторные рендеры,
   добавляем downsampling, виртуализацию, альтернативный рендерер,
   и сравниваем до/после при одинаковых условиях.

**Не делаем сейчас:** MobX, Web Workers, Canvas, оптимизации или
подключение реального backend. Всё это будут отдельные этапы после
измерения реального узкого места.
